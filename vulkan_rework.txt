Vulkan Ray Tracing Rework Plan
==============================

The current CPU architecture maps almost directly onto Vulkan's ray tracing model.
The goal is to eventually replace the CPU path tracer with a Vulkan RT pipeline,
but Vulkan has enough boilerplate that it's worth building up in stages rather
than attempting a full translation in one shot.


STAGE 1: Basic Vulkan Rasterization Pipeline
---------------------------------------------
Get comfortable with Vulkan before touching RT extensions. A rasterization
pipeline covers all the infrastructure that RT will also need.

Libraries (use all four from day one):
  - vk-bootstrap  : instance/physical device/logical device/swapchain in ~50
                    lines instead of ~400; do not hand-roll these
  - VMA           : replaces vkAllocateMemory + vkBindBufferMemory with one
                    call; RT requires heavy buffer allocation so this pays off
                    immediately in Stage 2
  - GLFW          : window + VkSurfaceKHR creation
  - GLM           : vec3/mat4 math that matches GLSL layout rules; important
                    for correct UBO alignment

Milestones:
  1. [DONE] Instance + device + swapchain + render pass
       vk-bootstrap handles instance/device/swapchain boilerplate. Validation
       layers enabled from the start. RT extension feature structs chained into
       device pNext (all bits FALSE) to confirm GPU support early.
       Semaphore free-list design: image_count+1 acquire semaphores; old
       per-image semaphore recycled on re-acquire. All sync resources
       (cmd bufs, render_finished, in_flight) indexed by swapchain image index,
       not frame-in-flight slot.

  2. [DONE] Draw a triangle (hard-coded vertex shader, pipeline, shaders)
       Positions and colors hard-coded in the vertex shader. Runtime GLSL→SPIR-V
       compilation via libshaderc (no pre-compilation step). Dynamic viewport and
       scissor state (VK_DYNAMIC_STATE_VIEWPORT / SCISSOR) so the pipeline object
       is never recreated on resize. Framebuffer resize support added: GLFW
       callback sets a flag; main loop calls Swapchain::recreate() +
       RenderPass::rebuild_framebuffers() then continues.

  3. [DONE] Load and draw the bunny mesh (vertex buffer, index buffer, depth buffer)
       Parse existing PLY files from bunny/reconstruction/ into CPU-side
       glm::vec3 vertex and uint32_t index arrays. Upload to device-local VkBuffers
       via VMA staging buffers (TRANSFER_SRC CPU → TRANSFER_DST DEVICE_LOCAL).
       Add depth attachment (VK_FORMAT_D32_SFLOAT) to the render pass; depth image
       owned by RenderPass and recreated alongside framebuffers on resize.
       Camera MVP passed as a push constant (mat4, vertex stage). Fragment shader
       computes face normals via dFdx/dFdy on world_pos and maps them to RGB —
       no CPU-side normal computation needed, gives flat-shaded face visualization.
       Note: Stanford bunny PLY uses X-up convention (not Y-up as assumed).

  4. [DONE] Orbit camera with a UBO (uniform buffer object)
       Camera struct owns a persistently-mapped VkBuffer (VMA AUTO +
       HOST_ACCESS_SEQUENTIAL_WRITE + MAPPED), descriptor set layout (binding 0,
       vertex stage), descriptor pool, and set. Orbit state is spherical
       (theta/phi/radius + target); left-drag orbits, scroll zooms with radius
       clamped to [0.05, 2.0]. GLFW callbacks route through a small AppState
       struct stored in the window user pointer alongside the resize flag.
       Pipeline layout uses the camera descriptor set layout; push constant
       removed. Vertex shader reads MVP from UBO at set=0 binding=0.

This is ~1800 lines of setup but you only write it once. Every subsequent stage
reuses the same device/swapchain/command buffer scaffolding.

Things to skip for now (add only when a later stage demands them):
  - Multiple render passes or subpasses
  - Additional descriptor sets beyond the camera UBO
  - Push constants, specialization constants, pipeline cache

Skip validation layers in a hurry, but you will regret it. Enable them from day one.


STAGE 2: Add RT Extensions (KHR_ray_tracing_pipeline)
------------------------------------------------------
Requires: VK_KHR_ray_tracing_pipeline + VK_KHR_acceleration_structure.
Check device support first — any RTX 2000+ or RX 6000+ card has it.

New concepts vs rasterization:
  - BLAS (Bottom-Level Acceleration Structure): one per mesh
    Upload triangle positions as a VkBuffer, call vkCmdBuildAccelerationStructuresKHR.
    Driver builds the BVH internally — no SAH code needed.
  - TLAS (Top-Level Acceleration Structure): one per scene
    Array of VkAccelerationStructureInstanceKHR, each with a 4x3 row-major
    transform and a BLAS reference. This is exactly the Instance model.
  - Shader Binding Table (SBT): maps geometry to shader groups.
    One entry per material type (BRD, glass, emissive, ...).

Milestone: shoot a ray from a hard-coded camera, return the barycentric
coordinates of the first hit as a color. No shading, no BVH code, just
confirm the pipeline is wired up.


STAGE 3: Translate the Path Tracer
-----------------------------------
Once the RT pipeline is confirmed working, translate the CPU logic to shaders.

Shader stage mapping:
  CPU                             GPU (GLSL)
  --------------------------------+------------------------------------------
  Camera::_cast_ray_for_color()  | raygen shader (ray generation)
  BRDMaterial::scatter()         | closest-hit shader (one per material type)
  PureTransparentMaterial        | closest-hit shader (separate shader group)
  Skybox::color()                | miss shader
  Triangle intersection          | built-in (no intersection shader needed)
  TriangleBVH8                   | BLAS (driver-managed)
  BVH8List / Instance            | TLAS + instance transforms

Things that need restructuring:
  - Bounce loop: _cast_ray_for_color uses a while loop. GPU options:
      a) traceRayEXT() recursion in the raygen shader (simple, depth-limited,
         loses GPU coherence quickly past ~4 bounces)
      b) Wavefront: raygen fills a ray buffer, closest-hit writes bounce rays
         to another buffer, dispatch again. Better throughput for deep paths.
    Start with (a) since it's a direct translation. Move to (b) if needed.
  - Virtual dispatch: replace with a materialID stored per-triangle in the BLAS
    geometry data. Closest-hit shaders are selected via the SBT, not vtable.
  - RNG: each pixel needs its own state. Store a PCG32 seed in a storage image
    or push constant seeded by (pixel_x * width + pixel_y + frame * prime).
  - Accumulation: render to a float RGBA storage image, average with prior
    frames using a running mean (current * (n-1)/n + new/n) or keep a
    separate sample count buffer.

Material data layout:
  Define a GPU-side struct matching BRDMaterial fields (diffuse, specular,
  emissive, roughness). Pack into a SSBO (shader storage buffer) indexed by
  materialID. PureTransparentMaterial gets its own SSBO with refractive_index.


ARCHITECTURE THAT CARRIES OVER UNCHANGED
-----------------------------------------
  - SAH BVH construction: irrelevant — driver builds it from triangle data.
  - SoALeaf / moller_trumbore_8 / aabb_test_8: irrelevant — RT cores do this.
  - The overall path tracing algorithm: direct translation.
  - BBox, camera math, skybox colors: rewrite in GLSL/GLM but logic identical.
  - PLY loader: still runs on CPU, uploads vertex/index buffers to GPU.

The Instance transform is the cleanest win: what took manual rot/rot_inv matrix
math in C++ becomes a single field in VkAccelerationStructureInstanceKHR.


ROUGH EFFORT ESTIMATE
---------------------
  Stage 1 (rasterization foundation)  : 1-2 weeks
  Stage 2 (RT pipeline + first ray)   : 3-5 days
  Stage 3 (full path tracer)          : 1-2 weeks

Total: 3-5 weeks for a faithful translation. The algorithmic work is
small — most time goes to Vulkan API plumbing and shader debugging.

Expected performance vs current CPU implementation (4:25 / frame at 4K, 1000spp):
  A mid-range RT-capable GPU (RTX 3070 class) would likely do the same frame
  in 10-30 seconds. High-end (RTX 4080+): potentially under 10 seconds.
  Wavefront path tracing and denoising (DLSS or OIDN) could push interactive
  framerates for lower spp counts.
